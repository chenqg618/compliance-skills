# 电商退货退款与库存回冲核对（免费版）

> **完全本地运行**：引擎已经打包在本技能里（`engine/` 目录）。
> 核对过程不需要联网、不需要 API Key、**没有调用次数上限**、材料不出本机。

## 什么时候用

**谁在什么时候用**：电商财务 / 会计 / 仓储在对账日、月末结账、盘点差异复核这类固定节点上，
必须先把「退货退款与库存回冲明细表」核一遍，才能确认退款付得对不对、退回来的货有没有真的入回库存。
这张表出错的后果是双向的：**多退 / 重复退**（钱出去了、货没回来）和**少退 / 漏回冲**
（买家投诉、库存被系统性少计）。两者都会在平台账单、库存账和月报上暴露，而且**结完账就很难倒查**。

**这张表会逐项核对什么**（免费版执行 5 类，逐条都带**原文行号**）：

1. **退款金额逐行复算** —— 退款金额 = 实收金额 − 运费扣除 − 包装扣除 − 折旧扣除，差 1 分钱也报。
2. **退款单号与退货单号一一对应** —— 同一退货单号或同一退款单号在表里出现两次以上即报
   （重复录入会让退款合计被重复统计、库存被回冲两次）。
3. **库存回冲数量与退货数量勾稽** —— 回冲数量 > 退货数量是硬错（P0）；
   回冲数量 < 退货数量只提示（P2，部分入库属正常，但要写清原因）。
4. **退款状态与到账金额自洽** —— 状态说已完成却查不到到账金额、状态还没完成却已经填了到账金额、
   到账金额 ≠ 退款金额，三种都报。
5. **关键字段空缺** —— 退货单号 / 退款单号 / 退货日期 / 退货数量 / 退款金额 为空或写占位符（待填、无、-）。

每条结论都带**原文行号与原文**，可被第三方用同一口径复算；
材料不足时**不给结论**，会明确列出还缺什么，也不会用默认值编出结论。

## 不包含什么

免费版**不执行**下面这几类（引擎的 `CHECKS_WITHHELD` 会如实列出，跑 `--sample` 也能看到）：

- **跨店铺 / 跨期间的汇总台账**（按店铺与月份汇总笔数、退款金额合计与回冲数量）；
- **按退款金额排序的追损清单**（把应追回 / 应补退的差额降序排列，≥2 条才出清单）；
- **差异归因**（把退款金额差异归到扣款规则、运费承担、折旧计提三类）。

## 怎么用

```bash
node scripts/run.mjs --sample                    # 先看样例（样例本身就是一张自洽的表）
node scripts/run.mjs --input 你的材料.json        # 跑自己的材料
node scripts/run.mjs --input 你的材料.json --json # 机器可读输出
```

入参两种写法都行：

- `{"text": "（把表的**表头**和若干行一起复制进来，Tab 分隔最稳）"}`
- 直接把「退货退款与库存回冲明细表」（**含表头**）从 Excel 复制成文本粘进 `.json` 里；
  文件不是合法 JSON 时会整体按纯文本材料处理。

必需列（缺任何一列就不给结论）：退货单号、退款单号、店铺、退货日期、退货数量、回冲数量、
实收金额、运费扣除、包装扣除、折旧扣除、退款金额、退款状态、到账金额。

## 出参

- `status`：`success` 才有结论；`insufficient_input` 表示材料不足，此时**没有** `result`、**没有** `findings`。
- `result.findings[]`：每条含 `level`（P0/P1/P2）、`category`、`line`（**原文行号**）、
  `message`（含算式与差额）、`advice`、`evidence`（原文片段）。
- `result.summary`：`rows / total / p0 / p1 / p2 / omitted / by_category / verdict`
  （`NO_ISSUE_FOUND` | `NEEDS_REVIEW` | `ERROR_FOUND`）。
- `result.scope`：本次执行的 `checks`、未执行的 `checks_not_run`、`executed_locally: true`、`network_used: false`。
- `result.checks_out_of_scope`：本工具**根本不做**的判断清单（边界诚实）。
- CLI 退出码：`0` 已执行检查 / `1` 没给入参 / `3` 材料不足 / `4` 入参读不到或无法解析 / `9` 未预期错误。

## 常见错法（本产品专属）

1. **扣除项的口径一边含费一边扣费**：实收金额取的是**买家实付**（已含运费），
   运费扣除却按"平台向我收的运费"填 —— 两边口径不同，退款金额整列都会差一个运费。
   先定：实收金额是买家实付还是订单净额，然后全表统一。
2. **折旧被算了两次**：商品折旧已经体现在退款金额里，又在「折旧扣除」列填一遍，于是复算时再减一次。
   本工具逐行复算会把它抓成"退款金额复算不符"，但口径本身要先定死。
3. **分次打款挤在一行**：一笔退款分两次到账，全填在「到账金额」里凑了总额 ——
   状态一改就对不上。正确做法是**拆成两行**（同一退款单号会出现两次，本工具会提示单号重复，
   这属于"如实提示"而非误报）。
4. **回冲数量按"件数"和按"箱数"混填**：同一个表里两种单位混用，
   回冲数量会整片偏离退货数量。单位写在表头或备注里，不要靠人记。
5. **状态栏用自己发明的写法**：例如「已打款待确认」「部分到账」。本工具只按
   表内已认得的「已完成 / 未完成」两类写法核对自洽性，认不出的写法会被跳过 ——
   宁可统一成两种写法，也不要让关键行静默不参与核对。

## 使用次数与完整档

本免费版每次运行结束后会向服务端做**一次匿名次数统计**：只发送本包标识和一个不含任何材料的匿名安装标识
（由主机名与用户名做短哈希得到），**不发送你的材料、不写任何文件**。

· 前 3 次：服务端不返回任何内容，输出与现在完全一样；
· 第 4 次起：服务端会返回一段**完整档说明**（完整档是另一个独立商品，条款与价格以它自己的商品页为准），届时才会打印这一行；
· 统计不可用（离线 / 超时 / 被拦截）时什么都不做，**核对结果与退出码不受任何影响**；
· 不想要这次统计可以加 `--no-stats`（核对功能完全不受影响，只是拿不到完整档说明）。

本版本不包含的检查项见上一节；需要完整档时按服务端返回的官方口令执行，付款由用户本人确认。
